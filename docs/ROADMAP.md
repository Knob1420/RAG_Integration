# 路线图（ROADMAP）

> 阶段门制度：每个阶段必须满足「通过标准」并经 Codex 依据实际 diff、测试和实验结果验收后，方可进入下一阶段。
> 阶段顺序不可跳过；阶段内部的路线调整必须通过 ADR（docs/decisions）记录。
> 时间估计为相对工作量估计（人日），非日历承诺。

---

## P00 项目范围与资料治理

- **时间估计**：2–3 人日
- **目标**：建立项目控制面；确认资料范围与安全等级；建立资料清单与问题池。
- **要掌握的知识**：阶段门管理、数据分级、provenance 基本概念、ADR 写法。
- **实践任务**：
  1. 建立本控制文档体系（本文件等）；
  2. 与用户确认资料范围与分级，形成资料清单报告；
  3. 建立问题池（候选 → 可验证 → 跨文档 → 冲突/不可回答）；
  4. 确认数据存放边界（原始资料路径不入仓库）。
- **产出**：docs/ 全部控制文件、docs/reports/P00-data-inventory.md、问题池初版。
- **检查方法**：逐项核对 docs/phases/P00-project-scope.md 的通过条件。
- **通过标准**：见 docs/phases/P00-project-scope.md。
- **进入下一阶段的条件**：资料清单与分级获用户书面确认；问题池含 ≥1 个可验证问题。
- **未通过时的处理**：阻塞项写回 CURRENT_STATUS.md，生成修复任务，不进入 P01。

## P01 数据解析与规范化

- **时间估计**：5–8 人日
- **目标**：把登记的资料解析为带 provenance 的规范化 Document/Chunk 结构。
- **要掌握的知识**：文档解析（PDF/表格/图文）、元数据与 provenance 设计、结构化输出、解析质量评估。
- **实践任务**：
  1. 设计 Document/Chunk/Source 数据模型（含 source_id 规范）；
  2. 实现各格式解析器；
  3. 表格与图文的特殊处理；
  4. 解析质量抽样检查与报告。
- **产出**：解析器代码 + 测试、规范化数据样例、解析质量报告、解析器版本记录。
- **检查方法**：抽样人工比对原文与规范化输出；自动化测试通过；source_id 回链抽查 100% 正确。
- **通过标准**：抽样解析正确率 ≥ 用户与 Codex 约定的阈值；所有 Chunk 可回链到原始页码/位置。
- **进入下一阶段的条件**：通过标准达成且解析质量报告经 Codex 验收。
- **未通过时的处理**：登记解析缺陷任务，修复或调整解析策略；必要时通过 ADR 缩小首版格式范围。

## P02 传统 RAG Baseline

- **时间估计**：4–6 人日
- **目标**：搭建最小可用的 BM25 + 向量检索 RAG，形成对照基线。
- **要掌握的知识**：信息检索、BM25、Embedding、Hybrid Retrieval 基础、基础引用回链。
- **实践任务**：
  1. 构建 BM25 索引；
  2. 构建 Embedding 索引（模型选型走 ADR）；
  3. 简单混合检索与融合；
  4. 带引用的回答生成链路（此阶段可用模板/规则，不强依赖 LLM API）。
- **产出**：索引构建代码、检索与回答链路、基线运行日志。
- **检查方法**：对问题池子集运行检索，人工核对 top-k 命中。
- **通过标准**：链路端到端可运行；每个回答带 source_id；不可回答问题能显式输出"证据不足"。
- **进入下一阶段的条件**：基线可复现运行，结果留档。
- **未通过时的处理**：回退修复检索或解析问题；不得为通过指标而降低引用要求。

## P03 评测体系

- **时间估计**：4–6 人日
- **目标**：建立可复现的评测集与指标体系，为后续优化提供标尺。
- **要掌握的知识**：RAG 评测（检索指标 / 生成指标 / 引用忠实度）、Gold Evidence 标注、Answerability 判定。
- **实践任务**：
  1. 构建标注评测集（问题 + Gold Evidence + 参考答案）；
  2. 实现检索指标（Recall@k、MRR 等）与回答指标（引用正确率、拒答正确率）；
  3. 对 P02 基线出首份评测报告。
- **产出**：评测集（脱敏）、评测脚本、P02 基线评测报告。
- **检查方法**：评测脚本可重复运行且结果一致（固定随机性）；指标定义与实现一致。
- **通过标准**：评测集规模与质量达约定门槛；基线指标入库作为对照。
- **进入下一阶段的条件**：评测报告经 Codex 与用户确认。
- **未通过时的处理**：扩充/修正评测集；指标定义不清则先写 ADR 澄清再测。

## P04 高级 RAG 与问题路由

- **时间估计**：5–8 人日
- **目标**：在基线上引入 Query 改写/分解、Reranker、表格检索、版本过滤，按问题类型路由。
- **要掌握的知识**：Query Rewrite、Query Decomposition、Reranker、表格检索、版本过滤、成本与延迟优化。
- **实践任务**：
  1. 问题分类路由器；
  2. Reranker 引入与对比实验；
  3. Query 改写/分解；
  4. 表格与参数类问题的专用链路。
- **产出**：路由与增强检索代码、对比实验报告（vs P02/P03 基线）。
- **检查方法**：评测体系回归对比；延迟与成本记录。
- **通过标准**：相对基线在约定指标上有可解释提升，且无引用正确率回退。
- **进入下一阶段的条件**：实验报告验收通过。
- **未通过时的处理**：逐项消融定位无效组件；无效组件移除并记录 ADR。

## P05 工程追溯图与 GraphRAG

- **时间估计**：8–12 人日
- **目标**：从规范化数据抽取实体与关系，构建追溯图，实现 GraphRAG 的 Local/Global 检索。
- **要掌握的知识**：知识图谱建模、实体链接、Entity Resolution、图遍历、Local/Global Search。
- **实践任务**：
  1. 本体与图 schema 设计（ADR）；
  2. 实体/关系抽取与实体消歧；
  3. 图存储与遍历查询；
  4. GraphRAG 检索接入主链路并与 P04 对比。
- **产出**：图构建管线、图数据（含 source_id）、GraphRAG 检索、对比评测报告。
- **检查方法**：实体/关系抽样核对原文；图查询结果回链证据；评测回归。
- **通过标准**：跨文档类问题相对 P04 有约定提升；图中实体/关系均可回链 source_id。
- **进入下一阶段的条件**：图质量与检索效果验收通过。
- **未通过时的处理**：缩小图范围（只保留高置信关系）；抽取质量不足则回 P01 补解析或补规则。

## P06 LLM Wiki

- **时间估计**：6–10 人日
- **目标**：生成带引用、可增量更新的领域 Wiki，作为人读的知识沉淀层。
- **要掌握的知识**：结构化生成、增量更新与版本管理、LLM 内容与 ground truth 的区分、Prompt Injection 防御（Wiki 生成读取资料内容）。
- **实践任务**：
  1. Wiki 页面结构设计（每条陈述带 Evidence 引用）；
  2. 生成管线（仅基于 Evidence，禁止无引用陈述）；
  3. 增量更新与冲突检测；
  4. 人工审核门。
- **产出**：Wiki 生成与更新代码、Wiki 初版页面、更新/冲突处理报告。
- **检查方法**：逐陈述抽查引用真实性；更新后引用完整性回归。
- **通过标准**：抽样陈述引用正确率 ≥ 约定阈值；无引用陈述数量为 0（或全部显式标注为待审）。
- **进入下一阶段的条件**：Wiki 质量经用户抽查认可。
- **未通过时的处理**：收紧生成约束、增加审核轮次；必要时降低自动化程度改为半自动。

## P07 Agent Memory

- **时间估计**：5–8 人日
- **目标**：为用户、任务和工作经验建立分型 Memory，与领域知识库、Wiki 明确区分。
- **要掌握的知识**：Agent 状态、Working/Semantic/Episodic/Procedural Memory、Memory policy（写入/衰减/删除）、权限与数据删除。
- **实践任务**：
  1. Memory 数据模型与 policy 设计（ADR）；
  2. 写入/检索/遗忘管线；
  3. Memory 与 RAG 主链路的融合与隔离；
  4. Memory 污染防护（错误记忆不进入知识库）。
- **产出**：Memory 模块、policy 文档、带/不带 Memory 的对比评测。
- **检查方法**：policy 行为测试（删除传播、衰减、越权访问拒绝）；对比评测。
- **通过标准**：Memory 不降低主链路指标；删除与权限边界测试全部通过。
- **进入下一阶段的条件**：对比评测与边界测试验收通过。
- **未通过时的处理**：收紧 Memory 写入门槛；回退到更保守 policy。

## P08 集成、部署与总结

- **时间估计**：5–7 人日
- **目标**：系统集成、本地部署、可观测性完备、项目总结。
- **要掌握的知识**：数据库和 API 基础、测试和可观测性、部署与回滚。
- **实践任务**：
  1. 端到端集成与统一入口（CLI/API）；
  2. 日志、指标、追踪（遵守数据治理约束）；
  3. 部署方案与回滚演练；
  4. 项目总结报告与知识盘点（对照 KNOWLEDGE_MAP.md）。
- **产出**：部署文档、可观测性面板/日志规范、最终评测报告、项目总结。
- **检查方法**：全量测试回归；部署演练可回滚；敏感信息泄漏扫描。
- **通过标准**：第一版成功标准（见 PROJECT_CHARTER.md）全部满足并留档。
- **进入下一阶段的条件**：项目结项或（经用户决策）开启下一版规划。
- **未通过时的处理**：缺陷登记修复；不可在结项报告中掩盖未达项。

## 阶段通用规则

1. 每阶段开始前：从 docs/tasks/TASK_TEMPLATE.md 复制任务包放入 docs/tasks/active/；
2. 每阶段结束：Codex 出阶段报告入 docs/reports/，任务包移入 docs/tasks/completed/；
3. 任何阶段未通过：阻塞项、原因、修复任务写入 CURRENT_STATUS.md，禁止带病推进；
4. 路线调整：写 ADR 至 docs/decisions/，涉及阶段顺序变更须用户确认。
